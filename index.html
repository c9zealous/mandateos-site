MandateOS

A working name · Sandbox stage · October 2026

Your agent can pay. Inside limits the user set. With proof.

MandateOS is the authorization and control layer for AI-agent payments in India. It decides, in real time, whether an agent may spend a user's money — and it writes the decision down, permanently, before any money moves.

01

What it is

A user grants an AI agent a scoped, revocable mandate: a per-transaction cap, a daily and monthly budget, merchant and category allowlists, a validity window, and rules for when the agent must ask first. Every payment the agent attempts is evaluated by a deterministic policy engine and returns one of three decisions — ALLOW, STEP_UP (ask the user, with full context, on their phone), or DENY — each with a machine-readable reason code the agent can act on. Every grant, decision, approval and execution is written to an append-only, hash-chained ledger.

MandateOS does not move money. It holds no funds, pools nothing, settles nothing. Licensed partner PSPs and banks execute on UPI — today that means UPI Reserve Pay blocks and e-mandates / UPI Autopay — and only on a decision the ledger already records. That separation is the design, not a limitation we are working around: an agent is never an authentication factor, and no rail call happens without a committed policy decision behind it.

The control layer for agent payments exists today only inside individual PSPs' walls. What does not exist is the neutral version: one mandate and policy layer an independent agent builder can use regardless of which PSP executes, with agent identity (“Know Your Agent”) and a dispute-evidence record on UPI. That narrower claim is the product. Whether buyers will pay a standalone fee for neutrality is, as of this writing, untested — the pilot described in §8 is the test.

02

How a decision works

This is the scripted demo, run against the real policy engine, ledger and approval flow. Priya has given her grocery agent a mandate: groceries only, BigBasket and Blinkit, ₹15,000 a month, ₹5,000 per transaction. ₹6,400 of the month's budget was already spent before the demo starts.

Beat 1 — the silent allow
  → request_payment(BigBasket, ₹3,850, GROCERIES)
  [ledger #4] POLICY_DECISION → ALLOW (IN_SCOPE)
  [ledger #6] EXECUTION_SUCCEEDED → rail txn sbx_txn_2

Beat 2 — the step-up
  → request_payment(Blinkit, ₹2,600, GROCERIES)
  [ledger #7] POLICY_DECISION → STEP_UP (FIRST_TXN_FOR_MERCHANT)
  [approval] ₹2,600 at Blinkit · first payment to this merchant
             under the mandate · budget left after: ₹2,150 · expires 10 min
  [ledger #9] APPROVAL_DECIDED → APPROVED by Priya (in-app)
  [ledger #10] POLICY_DECISION → ALLOW (IN_SCOPE_AFTER_APPROVAL)

Beat 3 — the hard deny
  → request_payment(Farmstory, ₹4,200, GROCERIES)
  [ledger #13] POLICY_DECISION → DENY (MERCHANT_NOT_ALLOWLISTED)

Finale — the kill switch
  [ledger #14] KILL_SWITCH_ENGAGED → AGENT
  → request_payment(BigBasket, ₹3,850, GROCERIES)
  [ledger #15] POLICY_DECISION → DENY (KILL_SWITCH_ENGAGED)

Ledger check: 15 entries, hash chain intact.

Disclosure, in the demo's own words: “The rail underneath today is a simulator we wrote; the policy engine, the ledger and the approval flow are the real product code. Live execution rides a partner PSP's mandate products — that integration is what the design-partner phase is for.” The approval in Beat 2 is decided on the user's own surface; no agent can approve its own request, and an approval is bound to exactly one amount and one merchant. It can satisfy a step-up rule. It can never enlarge the mandate.

03

The mandate

The mandate is the core object. These are its actual fields, from the frozen contracts (v1.3.0); amounts are integer paise, and defaults are clamped to regulatory maxima at creation.

FieldMeaning
cap_per_txn_paiseHard ceiling per transaction. A cap breach is a DENY, never a step-up.
cap_daily_paiseBudget over a rolling 24-hour window.
cap_monthly_paiseBudget over a rolling 30-day window.
merchant_allowlistMerchants the agent may pay, bound to merchant ID or VPA — never to a display name, so lookalike names do not pass.
categoriesPermitted spend categories. The agent's declared category is checked against the merchant's registered category; an agent cannot self-certify.
step_up_threshold_paiseAbove this amount, the user approves first, even when the payment is otherwise in scope. Zero means always ask.
approval_modeSilent within scope, or approve every transaction.
rail_constraintsWhich rails may execute, and the mandate's no-AFA ceiling per transaction.
valid_from / valid_untilThe validity window, at most five years. Outside it, every request is denied.

The default silent profile adopts the envelope regulators already accept for delegated UPI payments: ₹5,000 per transaction and ₹15,000 per month, taken from UPI Circle's full-delegation caps as a template.1 ₹15,000 is also the RBI e-mandate ceiling for recurring debits without additional authentication. Above the line, the agent asks. In the demo mandate above: per-payment cap ₹5,000, monthly cap ₹15,000, allowlist of exactly two merchants.

1 UPI Circle delegates between humans, so it is a template for caps and consent design only. It is never an execution path for agents, and no mandate is registered on it.

04

Every no has a code

Decisions are not vibes. Each one carries a reason code from a versioned registry — 32 codes today, never repurposed, never deleted — so an agent can react programmatically and a human can debug without guessing. Evaluation runs in a fixed order: kill switch first, then actor and mandate state, merchant, category, regulatory ceiling, caps, attestation, anomaly checks, step-up rules. Six of the codes, verbatim from the registry:

CodeDecisionMeaning
IN_SCOPEALLOWAll checks passed; silently executable on the chosen rail.
IN_SCOPE_AFTER_APPROVALALLOWA step-up approval completed and the payment was re-evaluated with the approval attached.
FIRST_TXN_FOR_MERCHANTSTEP_UPFirst transaction to this merchant under this mandate; the user must approve it.
MERCHANT_NOT_ALLOWLISTEDDENYThe allowlist is non-empty and the merchant is not on it.
CAP_PER_TXN_EXCEEDEDDENYAmount exceeds the per-transaction cap. Caps are DENY, never STEP_UP.
KILL_SWITCH_ENGAGEDDENYA kill switch is engaged, at global, developer, agent or mandate scope. Checked first, and checked again at execution time.

A DENY is terminal. No approval request is ever created for a denied payment — a user is never asked to bless something outside the scope they granted.

05

The evidence pack

When an agent spends inside a mandate and the user disputes it, someone has to answer a specific question: what exactly was this agent allowed to do, and what did it do? For any payment, MandateOS exports a dispute evidence pack that answers it from the record — the mandate as consented, the full decision chain, the approval record, and the execution reference, hash-linked. An excerpt from a real generated pack (the demo's Beat 2 payment, sandbox data):

## Summary verdict
The agent attempted a payment of ₹2,600 to Blinkit.
Final policy decision: ALLOW; payment status: SUCCEEDED.
Reason: IN_SCOPE_AFTER_APPROVAL — the user approved this payment,
and on re-check it was inside the mandate's scope.

## What happened
STEP_UP at 2026-10-23T11:33:00Z — FIRST_TXN_FOR_MERCHANT (ledger seq 22)
Approval: ₹2,600 to Blinkit via PUSH — APPROVED by the user (seq 24)
ALLOW at 2026-10-23T11:33:00Z — IN_SCOPE_AFTER_APPROVAL (ledger seq 25)
Execution: rail SANDBOX_UPI, external reference sbx_txn_7

## Verification
Ledger chain: valid. The user's full hash chain (28 entries) was
re-verified at generation time.

The same section of the real pack states its own limit, and so do we: packs are not server-signed in v1. The hashes prove the pack is internally consistent and that the ledger chain was intact when the pack was generated; they do not by themselves prove MandateOS issued it. Server signing is named future work, in the document itself.

06

Measured, not asserted

The policy engine is scored by an eval harness on every change: a golden corpus of decisions it must get right, and an adversarial suite of attacks a rogue or prompt-injected agent would try. Current scorecard, generated 2026-10-23:

SuiteResult
Golden decision corpus95 / 95 scenarios correct; every safety-gated category (caps, budgets, allowlist, attestation, kill switch, regulatory ceiling) at 100%
Adversarial suite10 / 10 attacks blocked, including payment structuring against the monthly budget, merchant spoofing, approval replay, tampered amounts after approval, cross-mandate credential use, and a kill switch engaged mid-flight
Ledger integrity5 / 5 scored tamper cases detected (mutated amount, deleted entry, reordered entries, forged hash)
Decision latencyp95 of 0.033 ms per evaluation, in-process, over 2,790 samples

Two limits, stated because the scorecard states them: silently dropping the ledger's tail entry is not detectable from the chain alone — it needs an externally anchored chain head, which is not built yet. And two registry codes (an API-layer idempotency conflict and the approval rate limit) are enforced outside the engine, so the corpus does not exercise them. The scorecard was generated against contracts v1.2.0; the contracts are now at v1.3.0.

07

Honest status

Real today

  • The policy engine, mandate lifecycle, step-up approval flow, kill switches and hash-chained ledger, running end to end.
  • A REST API, a native MCP server with the six agent tools, a TypeScript SDK, a developer console, and the mobile approval page.
  • Evidence pack export per payment, and a Razorpay adapter that runs in test mode.
  • The eval harness in §6, in the repo, runnable by anyone with the code.

Simulated, and labelled as such

  • The UPI rail in the sandbox and the demo is a simulator we wrote. It exists so the full loop — mandate, decision, step-up, execution, ledger — can be exercised and attacked today.
  • Sandbox identity verification (the step from self-asserted L0 to L1) validates the shape of submitted evidence only. Its records say so: verification_method: "SELF_ATTESTED_SANDBOX". It is not a real-world identity check.

Does not exist yet

  • Live UPI execution. That requires a partner PSP integration, and those conversations are the current phase. Anyone who tells you their agent layer is live and autonomous on UPI today is demoing a simulator and not saying so. We say so.
  • Any regulatory approval. None is claimed or implied. NPCI's Unified Agentic Protocol and agent registry are paused pending RBI sign-off; this product is built to be that protocol's policy engine if and when it is approved, and depends on it for nothing.
  • Production users, partner logos, testimonials. There are none, so this page shows none.

08

For builders

From a clone of the repository, one command takes you to your first ALLOW decision, over the public API: fresh developer account, agent registered and verified to L1, mandate consented, first payment stepped up and approved, second payment allowed silently, ledger verified.

npm run quickstart

Your agent talks to MandateOS over MCP (Streamable HTTP at POST /mcp) or REST. The MCP surface is exactly six tools: check_mandate, list_my_mandates, request_payment, get_payment_status, request_mandate, cancel_payment. There is deliberately no approve tool and no mandate-edit tool on the agent surface: an agent can never approve its own spend or widen its own mandate. Agent credentials are scoped per agent and per mandate, and signed; a token minted for one mandate is worthless against another.

References: the code repository is private during the design-partner phase, and the SDK guide (@mandateos/sdk, with runnable examples) ships inside it. Public for now: the sample evidence pack from §5, also available as the raw Markdown file. The hosted sandbox with self-serve keys is the next build item; until it ships, sandbox access comes with the pilot call below.

09

The proposed standard

The object that matters in agent payments is not the credential. It is the mandate. We have drafted the mandate object, its lifecycle, its decision vocabulary and its mappings to AP2, Visa's Trusted Agent Protocol and Mastercard's Verifiable Intent as a proposed open standard, so the format outlives any one vendor — including us.

It is a proposal by an independent developer, currently in preparation for publication. It is not issued by, endorsed by, or affiliated with NPCI, the Reserve Bank of India, or any payment network, and nothing in it authorizes anyone to move money. Read the draft — forthcoming; it will be published here when it is ready.
